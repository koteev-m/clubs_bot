Статус: **ACCEPTED_DECISION**, прямое решение владельца продукта 2026-11-09.
Новая локальная задача `CLB-owner-manager-ux`, repository `koteev-m/clubs_bot`,
base `16761e43887036688028358524847db1af0e5326` (merged PR #566).
Это уточнение DEC-004/005/040/041 и [PRODUCT_SPEC §29.17](../product/PRODUCT_SPEC.md#owner-manager-model),
без нового номера решения. Source concept неизменяем. Исторический

Принятое поведение и факт локальной реализации/проверок/развёртывания различаются.

## Целевые роли и совместимость

| Роль | Целевая ответственность |
|---|---|
| Владелец сети | Контроль собственной сети и клубов |
| Владелец клуба | Контроль результатов, персонала и важных решений, возможность своей настройки |
| Управляющий сети | Просмотр и сравнение реальных показателей назначенных клубов, контроль подготовки и координация без автоматических полных настроек |
| Управляющий клуба | Подготовка и текущее управление конкретным клубом |
| Менеджер | Разрешённые менеджерские операции и столы, включая обязанности прежнего Host |
| Менеджер входа | QR, гостевые списки, поиск, приход и отказ |
| Финансовый менеджер | Финансовая ответственность после отдельного permission/operation contract |
| Промоутер | Промоутерские функции; scope требует отдельного принятия |
| Гость | Гостевые функции в разрешённой витрине |

Отдельного Host нет; DJ, Администратор клуба, Менеджер зала и прежние сетевые
административные должности исключены из основного target catalogue. Владелец сети
и клуба контролируют свои области доступа, не платформу. Сетевой кабинет и
network permissions здесь не реализуются. Сопоставление этих target ролей с
техническими кодами требует отдельной безопасной RBAC-миграции.

Текущие `ENTRY_MANAGER` (read), `MANAGER` (read/profile/layout/calendar/booking rules)
и `CLUB_ADMIN` (то же плюс finance/modules configuration) остаются без изменения.
Это technical packages, не автоматическое соответствие новому catalogue.
ENTRY_MANAGER не получает QR/check-in по совпадению названия. Existing assignments,
legacy/GLOBAL authority и inactive grants сохраняются; массовой миграции нет.

## Owner authority и назначение

Создание private club и immutable creator не меняются. Подтверждённый создатель
с active client/membership/mapping и требуемыми existing read/team.manage управляет
процессом в конкретной паре client/club. Body IDs, role metadata, client membership
и legacy OWNER/GLOBAL не заменяют серверную проверку.

После успешного создания предлагается: «Назначить ответственного за подготовку»,
«Настроить самостоятельно», «Назначить позже». Владелец всегда может отдельно
открыть настройки, разрешённые его текущими grants. Ответственность по подготовке
не передаёт ownership, team.manage или platform authority.

Новый сотрудник приглашён через прежний staff invitation: случайная одноразовая
Telegram-ссылка, hash-only secret в БД, signed Telegram identity, claim кандидата
и отдельная сверка/подтверждение владельцем. До последнего шага grants нет.
Назначение связано с клубом, invitation и подтверждённым assignment; ошибочный
кандидат, expiry или revoked access не создают мнимого успешного назначения.
Уже подтверждённый подходящий сотрудник может назначаться только после fresh
проверки текущего assignment и действующих permissions.

Temporary access для подготовки — полный existing CLUB_ADMIN. Владелец должен
иметь authority выдать весь пакет, иначе операция отклоняется целиком. UI поясняет:
«Ответственный за подготовку: доступ к настройкам клуба, без управления сотрудниками,
денежных операций и прав собственности». Это не новая техническая роль управляющего.
Новые permissions, частичная выдача и автоматическое восстановление tombstones запрещены.

## Сохраняемый lifecycle

| Состояние | Проверяемый смысл |
|---|---|
| Ответственный не назначен | Подготовка никому не поручена; можно выбрать позже |
| Приглашение ожидает принятия/подтверждения | Сохраняемая связь с pending staff invitation; grants ещё не подтверждены |
| Подготовка в работе | Самостоятельная работа владельца либо подтверждённый назначенный сотрудник |
| Отправлено на проверку | Результат явно передан владельцу |
| Принято владельцем | Владелец принял настройку, без публикации клуба или открытия бронирований |
| Возвращено на доработку | Владелец сохранил причину, ответственный может продолжить разрешённую настройку |

Статус хранится на сервере после перезапуска и не выводится из одного frontend
состояния, количества заполненных полей или публичности. Назначенный сотрудник
видит свои доступные задачи и сохранённые значения. Передача на проверку требует
текущего assignment и действующих grants; список разделов не расширяет authority.
Профиль, расписание/ночи, залы/зоны/схемы/столы, booking rules, финансовые шаблоны,
module settings и подробная готовность доступны только по existing active grants.

Владелец проверяет сохранённый результат и незавершённые пункты, принимает либо
возвращает с причиной. Readiness не выдумывает данные/финансы/отчёты. «Данных пока
нет» и «Проверка недоступна» различают отсутствие источника и невозможность проверки.
Технический checklist находится в отдельной «Проверке готовности», а ежедневный
обзор отвечает «Как работает мой клуб и что требует внимания?».

Снятие назначения и отзыв staff access — отдельные действия. Первое прекращает
ответственность по задаче, сохраняя grants; второе блокирует дальнейшие операции
по действующим правилам staff revoke. UI явно объясняет разницу. Ни одно действие
не восстанавливает права автоматически. Отзыв доступа не отменяет прошлые записи
и не отбирает уже раскрытые с устройства данные.

## Технические инварианты

Каждый read/write/replay проверяет конкретного actor/client/club, активные
membership/mapping/grants и relevant assignment; owner actions подтверждают
immutable creator. Версия процесса защищает stale writes. Durable idempotency
связывает actor/target/intent и не допускает повторного эффекта; mutation, command
receipt и audit коммитятся атомарно. Client/club locks сериализуют конкурентные
назначения, staff revoke/confirm и переходы. Audit failure откатывает весь результат.
Существующие APIs конфигурации сохраняют собственные versions/permissions/audit.

Новый preparation record — минимальная additive persistence H2/PostgreSQL, не
вторая authorization system. Доступ к работе не следует только из preparation
assignment: при staff revoke или потере необходимых grants новые действия
блокируются. Cross-client/club IDs не раскрывают данные. Старые HTTP responses
не возвращают права или значения прежнего клуба; авторизованный repeat не
переиспользует результат после потери current authority.

Unknown commands сохраняют body/key до выяснения результата. Черновики защищены
при internal/browser/Telegram Back и переключении контекста. Shell, routes,
history, Telegram BackButton и light/dark остаются общими, mobile 320/390 px.
Secrets, initData и raw Idempotency-Key не логируются и не пишутся в browser storage.

## Календарь

Default — «Предстоящие ночи», отдельно «Постоянное расписание» и «Особые даты».
Показываются business date и реальные даты/часы открытия/закрытия в IANA TZ клуба,
сохранённое/сформированное состояние и действие просмотра/изменения. «Ночь пятницы»
может открыться в субботу в 00:00 и закрыться в субботу в 08:00. Пользователь
выбирает дни и часы; для неоднозначного отношения времени к дате нужен явный выбор.

Сохраняются canonical business date, weekly/holiday/exception priorities,
DST gap/overlap handling и current calendar contracts. Перед записью — итоговый
интервал/изменения и предупреждение о protected data. Save schedule отдельно от
materialize persistent nights; связанные bookings не меняются; events, bookings,
HOLD и публичные ночи автоматически не создаются.
