## PostgreSQL и состав тестов

Учтены модуль, класс, имя метода или параметризованного вызова и результат. SHA-256 двух скачанных ZIP совпали с дайджестами GitHub для артефактов 15061496029 (H2) и 15063041857 (PostgreSQL). Количество включает существующие пропуски JUnit. Суммарные длительности случаев часто перекрываются, особенно между модулями.

| PostgreSQL, все модули кроме core-data | 1 471 | Группа `application`. Сохранён второй запуск тестов app-bot со своим значением Flyway locations |

В исходном PostgreSQL-отчёте 2 437 случаев (2 426 passed, 11 ignored). Маршрут кандидата выбирает 1 962 случая для PostgreSQL и сохраняет все 2 437 уникальных идентификаторов в объединении двух профилей. Одна ветвь Gradle-фильтра включает новые тесты в двух указанных пакетах, другая охватывает остальные пакеты. Все JVM-модули кроме core-data по-прежнему обнаруживаются командой `test`. [Отчёты исходного прогона](https://github.com/koteev-m/clubs_bot/actions/runs/45694799240)

Каждая группа получает свой runner и сервис PostgreSQL. Опция `--rerun` относится к тестовым задачам. Каждый worker проверяет свежий XML заведомо PostgreSQL-зависимого класса, включая результат Testcontainers. Для Flyway по-прежнему обязательны оба исходных метода с точным составом. `fail-fast: false` позволяет остальным группам завершиться при ошибке соседа. `tests-required` требует успеха H2 и всей PostgreSQL-матрицы.

## Что запускается на PR

Во всех строках остаются Gitleaks, файловый Trivy, проверка структуры релиза и итоговые `lint` и `release-state`. Под backend-проверками здесь понимаются H2/JVM, PostgreSQL, coverage, логи, платежи, Detekt/SARIF, проверка графа зависимостей, JVM Trivy и проверки образа. На PR проверяются обе архитектуры образа на точном SHA кандидата, контейнерный smoke собирается из фактического merge tree.

| Изменение | До | После |
| --- | --- | --- |
| Обычная документация | Документационный маршрут | Тот же маршрут. Изменение документации также позволяет переиспользовать слой сборки при публикации образа на main |
| Исходники Mini App / упакованный dist | Typecheck, Vitest, Vite, проверка ресурсов. Для dist также образ и smoke | Те же проверки |
| Обычная бизнес-логика backend | Backend, единый PostgreSQL | Backend, три изолированные группы PostgreSQL |
| Репозиторий в core-data | Полный маршрут с инфраструктурой | Backend. Для входов регрессионных проверок quality gates дополнительно выполняется selfcheck |
| Авторизация и платежи | Критические backend-пути обычно включали полный маршрут | Backend, Mini App для клиентских контрактов, selfcheck для затронутых входов платёжных и миграционных проверок |
| Версионный SQL в каноническом каталоге Flyway | Полный маршрут | Backend, применение миграций, история и checksum, совместимость схемы и запуск контейнера. Для V056 также selfcheck |
| CI, общие зависимости, инфраструктура, нестандартный путь или режим файла | Полный маршрут | Полный маршрут, все 122 corrected-stage и 73 strict release-state теста |
| Смешанные правки, переименование, удаление | Объединение затронутых путей | Объединение областей, включая старый путь и изменения в фактическом результате слияния |

Отдельные workflow заново определяют диапазон Git по общему классификатору. В исходном Lint #573 это заняло 10 с. Статусы PR и push вычисляются заново, поскольку у merge-кандидата и фактического main могут различаться деревья.

На реальном диапазоне PR #574 результат меняется с `full` на `ui-backend` без длинного selfcheck. Четыре corrected-задания и шаги strict release-state и selfcheck занимали в исходном main-прогоне в сумме **93:13 времени runner'ов**. Они работали параллельно. Фактическая экономия сквозного времени кандидата ещё не измерена. CI Guard также запускает существующие валидаторы workflow сразу после проверки закреплённых actions, параллельно с обязательными проверками.

## Кеш, HTTP 429 и граница повторного использования

Первая попытка сборки amd64 PR #574 получила Maven Central HTTP 429 для Kotlin 2.2.20 при конфигурировании `buildSrc`. В исходном JVM-задании setup-gradle предупреждал о неизвестном `cache-key-prefix`, получил HTTP 400 от cache service и восемь ошибок записи кеша. [Неудачный PR job](https://github.com/koteev-m/clubs_bot/actions/runs/45679290586/job/139435278258) · [JVM unit-tests](https://github.com/koteev-m/clubs_bot/actions/runs/45694799240/job/139489334841)

Семь workflow используют закреплённый setup-gradle v6.2.0 с открытым провайдером `basic`. Один и тот же ключ распределяется между заданиями по ОС, архитектуре и хешу Gradle-файлов. Записывать его может только unit-tests при push в main. Узкий статический анализ и три PostgreSQL-группы читают его, как и PR. Строгая проверка зависимостей сохранена. Docker хранит дистрибутив Gradle с проверяемой SHA-256 в экспортируемом слое. Сборки PR и smoke могут читать BuildKit-кеш публикации. Gradle-зависимости в Docker используют локальный cache mount для своей архитектуры. На новом builder при изменившемся слое `installDist` остаются загрузки из Maven Central, поскольку GitHub-экспорт слоёв не переносит содержимое mount. PR пишет в своё пространство архитектуры, smoke загружает образ только локально. [Контракт закреплённого action](https://github.com/gradle/actions/blob/3f131e8634966bd73d06cc69884922b02e6faf92/setup-gradle/action.yml) · [Кеш BuildKit в GitHub Actions](https://docs.docker.com/build/cache/backends/gha/)

Разрешены максимум три попытки для двух точных команд Gradle — проверки `help` и Docker `installDist`. Для повтора каждый конечный диагноз ошибки конфигурации должен указывать на ответ Maven Central 429 на GET/HEAD, до исполнения задач. У ошибок тестов, компиляции, проверки зависимостей, смешанной причины и неизвестной диагностики сохраняется первый отказ. Во всех случаях запускаются обычные проверки новой ревизии. PR-сборка выводит файл со своим SHA в `image-evidence/` до Buildx. Каталог исключён из контекста сборки, а проверяемая метка образа и выгрузка свидетельства в GitHub сохранены. Публикация на main сохраняет отдельные multi-arch, signature, provenance, SBOM и Trivy gates.

## Ориентиры времени

Для документации остаётся порядка 1–2 минут до обязательных статусов при обычной очереди. Для Mini App исходный worker занял 36 с, но проверка упакованных ресурсов включает образ обеих архитектур и smoke. Ориентир 3–5 минут зависит от доступности слоёв и сети. Эти оценки относятся к обязательным статусам. Публикация в main имеет собственную длительность. До изменений близкий пример с исходниками и dist Mini App дал 3:19 для Lint и 1:34 для Secret Scan на main. На PR вторая попытка Lint заняла 3:46, от создания прогона до успешного статуса прошло 10:29 из-за неудачной первой попытки amd64. [Lint на main #573](https://github.com/koteev-m/clubs_bot/actions/runs/45629590456) · [Secret Scan на main #573](https://github.com/koteev-m/clubs_bot/actions/runs/45629590809) · [Lint PR #573](https://github.com/koteev-m/clubs_bot/actions/runs/45626037125)

По исходным отчётам на три новые PostgreSQL-группы приходится примерно 1 165, 986 и 874 с суммарного времени тестов. Инженерная оценка для backend/миграции без полного selfcheck — порядка **18–25 мин** при сопоставимых runner'ах и своевременном старте всех трёх групп. Параллельность модулей, кеши, конкуренция за runner'ы и Docker меняют эти величины. Разделение добавляет время инициализации двух заданий при каждом запуске PostgreSQL. Тариф и лимиты runner'ов в этой задаче не менялись. Для полного маршрута существующая последовательность security-анализов и strict release-state одна заняла около 26:35. При сохранённых изолированных миграциях расчёт пока превышает цели 5–10 и 10–15 минут. Время GitHub у кандидата предстоит измерить.

## Проверка кандидата

Локальный прогон Java 21 на macOS ARM64 занял 4:09 для H2 и связанных задач, 63 из 137 задач выполнены, 74 взяты из Gradle-кеша. Тестовые задачи запущены с `test --rerun`. Все 1 762 идентификатора и статуса совпали с исходным H2-отчётом, JUnit XML содержит один прежний пропуск и ноль ошибок. Прошли coverageGate, checkLogsPolicy, ktlintCheck, detektGate, dependencyGuard и проверка разрешённого графа зависимостей. Два отрицательных запуска Gradle отклонили неизвестную группу и запуск группы без `-PrunIT=true`.

На приёмке воспроизведён неожиданный пропуск в соседнем классе при успешном контрольном тесте. Теперь каждая группа проверяет все свои свежие JUnit-отчёты. Допускаются только 11 конкретных ранее пропущенных случаев в соответствующих модулях и группах. Любой из них может перейти в успешный статус.

Все три команды PostgreSQL также отработали локально. Каждая прошла собственную проверку свежего XML.

После объединения четырёх локальных отчётов совпали **2 437 из 2 437** исходных идентификаторов и их статусы, включая все 11 прежних пропусков. Ни одного отсутствующего, лишнего или изменившего результат случая. С учётом повторов между профилями общее число исполненных или зарегистрированных как пропуски случаев сократилось с **4 199 до 3 724**. Все 475 исключённых повторов отдельно нашлись в фактическом H2-прогоне. В PostgreSQL совпали результаты двух исходных тестов Flyway и обязательных проверок в двух других группах.

Локально группы работали с перекрытием на одном Mac, на отдельных портах и базах PostgreSQL 16.14. Использовались Corretto 21.0.2, Docker Desktop и явный тестовый URL. `GITHUB_ACTIONS` был снят для всех трёх, `CI=true` — у application и data-client. В исходном hosted-прогоне использовались Linux amd64, Temurin 21.0.13, закреплённый сервис PostgreSQL 16.11 и Testcontainers PostgreSQL 16.16. Измеренные локальные длительности сопоставимы по составу тестов, но содержат конкуренцию за ресурсы одного хоста и другое окружение.

Проверки классификатора и топологии прошли 32/32, JVM workflow и свидетельств PostgreSQL — 19/19, PR image — 16/16 (32 утверждения). Валидатор прочитал все 32 workflow. Пройдены исходная проверка SHA всех actions, проверки полномочий, структуры платежей и релиза, а также четыре новых теста Gradle-кеша и retry. Действующие правила main требуют `lint` и `release-state` для актуальной базы слияния. [Правила main](https://github.com/koteev-m/clubs_bot/rules?ref=refs%2Fheads%2Fmain) Проверены позитивные и негативные фикстуры затронутых секций selfcheck, включая отсутствующий worker, удаление проверки миграции, устаревший XML, scope при удалении и переименовании, смешанный diff и собственные изменения CI. 122 corrected-теста и 73 strict release-state теста сохранены в полном маршруте. ## Локальная проверка Docker

На ARM64 первая сборка выполнила строгий `installDist` за 6:03. На готовом образе проверены UID/GID 10001, версии системных пакетов, Java 21 и четыре исполняемых launcher. В отдельной сети с PostgreSQL оба HTTP-запроса, `/ready` и `/health`, вернули 200.

В контролируемой паре использованы одна копия исходников, один builder и прогретый кеш зависимостей. Первая сборка заняла **20,5 с** с выполнением слоя `installDist`. Перед второй добавлен единственный файл Markdown в `docs/`. Сборка заняла **1,4 с**, BuildKit отметил `installDist` как `CACHED`. Во второй паре менялись только файл со значением SHA кандидата и OCI-метка ревизии. Результат — **25,1 с** с выполнением слоя и **1,4 с** с кешем. У финальных образов разные ID и метки и идентичные слои файловой системы. Это замеры локального переиспользования слоя. Обмен кешем через сервис GitHub, amd64 и время очереди этим экспериментом не проверялись.

Полный запуск кандидата в GitHub Actions, доступность сетевого кеша и сканеры amd64/arm64 ещё не проверялись для этой рабочей копии. После завершения CI в Draft PR нужно сопоставить длительности трёх групп и критический путь с исходным Lint 45694799240. Время полного режима характеризует изменение CI.
